Model Evaluation Report — Insider Threat Detection (UEBA)

1. Project Overview

Project: Insider Threat Detection using User Behavior Analytics (UEBA)

Objective: Detect unusual employee activity using machine learning and rule-based risk scoring, then make alerts available for investigation in Splunk.

Technology stack:

- Python
- Pandas and NumPy
- Scikit-learn
- Isolation Forest
- Splunk SPL
- Google Colab

Dataset: Synthetic employee activity logs generated for this project.

The system identifies potentially suspicious events using activity time, data-transfer volume, number of files accessed, sensitive-resource access, and machine-learning anomaly predictions.

«Important: An anomaly is an investigation lead, not proof of insider abuse or malicious intent.»

2. Dataset Description

The synthetic dataset contains the following fields:

Field| Description
"timestamp"| Time of the simulated activity
"user_id"| Synthetic employee identifier
"hour"| Hour of activity, from 0 to 23
"bytes_transferred"| Number of bytes transferred
"files_accessed"| Number of files accessed
"sensitive_access"| Indicator for sensitive-resource access
"label"| Synthetic ground-truth label: 1 = simulated suspicious event, 0 = normal
"ml_prediction"| Isolation Forest prediction: -1 = anomaly, 1 = normal
"ml_anomaly"| Converted anomaly flag: 1 = anomaly, 0 = normal
"risk_score"| Combined score from model and rule-based signals
"severity"| LOW, MEDIUM, HIGH, or CRITICAL
"alert"| Indicates whether the event meets the alerting criteria

The initial demonstration dataset contains 2,000 events, including 100 synthetically labelled suspicious events.

These labels are generated by simulation rules and do not represent verified real-world incidents.

3. Detection Methodology

3.1 Machine-learning detection

The project uses Isolation Forest, an unsupervised anomaly-detection algorithm.

The model uses these features:

- Hour of activity
- Log-transformed data-transfer volume
- Number of files accessed
- Sensitive-access indicator

The model predicts:

- "-1": Anomalous event
- "1": Non-anomalous event

The "label" field is not used to train the Isolation Forest model.

3.2 Rule-based risk scoring

The demonstration risk score uses the following weights:

Signal| Points
ML anomaly| 30
Off-hours activity| 15
Transfer of at least 10 MB| 25
Access to at least 20 files| 20
Sensitive-resource access| 10

The maximum possible score is 100.

Severity bands:

Score| Severity
0–24| LOW
25–49| MEDIUM
50–74| HIGH
75 or above| CRITICAL

An event is alerted when its risk score is at least 50 or the ML model flags it as anomalous.

These weights and thresholds are illustrative and should be tuned against representative validation data.

4. Evaluation Method

4.1 Initial exploratory evaluation

The initial notebook compares Isolation Forest predictions against the synthetic labels.

This provides a basic demonstration of evaluation metrics, but it is not a reliable estimate of real-world performance because the synthetic labels are based on activity patterns that may overlap with the features used by the model.

4.2 Recommended time-based evaluation

For a stronger evaluation:

1. Sort the events chronologically.
2. Use earlier events for training.
3. Use a later period for testing.
4. Keep test labels out of model training and threshold tuning.
5. Compare Isolation Forest with a rule-only baseline.
6. Calculate precision, recall, F1-score, and the confusion matrix.
7. Record the selected thresholds and test-period dates.

For example, the first 70% of the timeline could be used for training and the final 30% for testing, provided the split contains sufficient examples of both classes.

Because the initial synthetic generator assigns labels using specific patterns, this evaluation still measures performance only on the simulated environment, not on real employee behavior.

Metric definitions

Precision

The proportion of flagged events that are labelled suspicious.

Precision = TP / (TP + FP)

Recall

The proportion of labelled suspicious events detected by the system.

Recall = TP / (TP + FN)

F1-score

The harmonic mean of precision and recall.

F1 = 2 × Precision × Recall / (Precision + Recall)

Confusion matrix

The confusion matrix shows true positives, false positives, true negatives, and false negatives.

If a denominator is zero, the corresponding metric requires explicit handling rather than an assumed result.

7. False Positives and False Negatives

False positives

A false positive is an event predicted as suspicious even though its synthetic label is normal.

Possible examples include:

- An authorized overnight data transfer.
- A legitimate bulk file operation.
- A user accessing many files as part of their job.

Potential improvements:

- Establish user-specific behavioral baselines.
- Include job role and approved maintenance windows.
- Validate alert thresholds on a separate dataset.
- Correlate multiple independent signals before escalating an alert.

False negatives

A false negative is a simulated suspicious event that the detector fails to flag.

Potential reasons include:

- The activity resembles ordinary behavior.
- The risk score remains below the alert threshold.
- The anomaly model fails to identify the pattern.
- The synthetic dataset does not represent that attack pattern adequately.

Potential improvements:

- Review missed events.
- Add relevant features.
- Tune the model on validation data.
- Compare ML-only, rules-only, and combined approaches.

8. Limitations

- The dataset is synthetic and may not represent real organizational behavior.
- Synthetic labels reflect the assumptions of the generator.
- The model has not been validated against real insider-threat incidents.
- The initial exploratory evaluation may overstate usefulness.
- Risk scores are heuristic priorities, not calibrated probabilities of malicious activity.
- A flagged user must not be considered guilty solely because of an anomaly.

9. Future Improvements

1. Implement a strict chronological train/test split.
2. Compare Isolation Forest with rule-only detection.
3. Test additional anomaly-detection algorithms.
4. Add user-specific activity baselines.
5. Perform threshold tuning on validation data only.
6. Track false positives and false negatives.
7. Create automated tests for the detection pipeline.
8. Validate the approach using an appropriate, safely handled security dataset.
9. Add Splunk dashboard screenshots and investigation examples.

10. Conclusion

This project demonstrates a basic UEBA workflow that combines unsupervised anomaly detection with rule-based risk scoring and Splunk investigation searches.

The current implementation is a learning and portfolio prototype using synthetic data. Its metrics should be treated as exploratory until a separate, time-based evaluation has been completed.

The next development goal is to establish a reproducible evaluation process and compare detection approaches before making claims about effectiveness in a real SOC environment.
